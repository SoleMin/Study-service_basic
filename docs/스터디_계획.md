# 7주 AI 엔지니어링 단체 스터디 (5명 기준)

7주 동안 Docker, FastAPI, RAG(LangChain), Kubernetes를 익혀 마지막 주에 "k8s 위에 배포된 RAG API"를 팀으로 완성하는 스터디예요. 7주 동안 함께 쓴 팀 위키가 그 RAG API의 문서가 돼서, 데모 주제는 "우리 팀 위키에 질문하기"예요.


## 운영 방식

매주 단체 세션 1회(2시간)와 개인 과제(하루 최대 2시간, 주 3일, 약 6시간)를 조합해요. 5명 기준이고, 시간은 기본값이니 팀 상황에 맞게 고치세요.

| 구분 | 시간 | 하는 일 |
| --- | --- | --- |
| 개인 과제 | 하루 최대 2시간, 주 3일 (약 6시간) | 개념 학습, 실습 체크리스트, 위키 페이지 작성 |
| 단체 세션 | 주 1회 2시간 | 발표 30분 + 함께 실습 60분 + 코드 리뷰와 Q&A 30분 |
| 비동기 공유 | 수시 | 막힌 점은 채팅방에 에러 메시지와 함께 올리기 |

**주간 리듬 예시 (하루 2시간 이내)**

- 1일차: 개념 학습, 개인 위키 페이지로 정리
- 2일차: 실습 체크리스트 진행
- 3일차: 실습 마무리, 단체 세션 전날까지 PR 제출
- 단체 세션 날: 세션 2시간만 하고 개인 과제는 쉬기
- 나머지 날은 프로젝트에 쓰거나 쉬어요

**체크리스트 읽는 법**

- 표시 없는 항목은 필수예요. 이것만 끝내도 그 주는 완료예요.
- "선택 (하나만)" 목록에서는 시간이 남을 때 **딱 하나만** 골라요. 에이전트 선택 트랙도 이 하나에 포함돼요.

**역할 로테이션 (매주 바뀜)**

- **발표자**: 그 주 주제의 핵심 개념을 15분 발표하고, 함께 할 실습을 준비
- **리뷰어**: 다른 멤버 PR 2개 이상에 리뷰 달기
- **기록자**: 세션 중 나온 질문과 답을 팀 저장소의 `notes/`에 정리하고, 그 주에 팀 위키로 올라온 페이지 목록도 함께 정리
- **진행자**: 세션 시간표를 지키고, 막힌 사람을 채팅방에서 먼저 챙기기
- 5명이라 리뷰어는 2명이에요. 발표자 1, 리뷰어 2, 기록자 1, 진행자 1로 매주 한 칸씩 돌려요.

**공유 규칙**

- 팀 GitHub 저장소 하나에 각자 `members/<이름>/` 폴더로 개인 과제를 올리고, 팀 프로젝트는 `team/`에서 개발
- 개인 과제는 단체 세션 전날까지 PR로 제출
- 바이브 코딩은 자유롭게 쓰되, PR 설명에 "왜 이렇게 동작하는지" 3줄을 꼭 쓰기
- 하루 2시간을 넘기면 그날은 멈추고, 못 한 항목은 PR 설명에 "못 한 것"으로 적기. 다 못 해도 PR은 올리기

**API 키와 비용 규칙**

- API 키는 `.env`(로컬)와 k8s Secret(6주차)에만 두고, 저장소에는 `.env.example`만 올려요. `.gitignore`에 `.env`를 먼저 넣어요.
- LLM API 계정에는 월 사용 한도를 걸어 둬요. 금액은 팀이 정해요.
- 임베딩은 로컬 모델(`BAAI/bge-m3`, 한국어 지원)을 기본으로 써요. 처음 한 번 수 GB를 내려받지만 그 뒤로는 요금이 들지 않아요. 노트북 사양이 부족하면 팀이 합의해 API 임베딩으로 바꾸되, 팀 전체가 같은 모델을 써요.

## LLM 위키 운영 (개인 위키 → 팀 지식 베이스)

- **목적**: 학습 노트를 위키 형식으로 바꿔 쓰는 것이라 시간이 따로 들지 않아요. 7주 동안 쌓인 팀 위키가 7주차 RAG API의 문서 데이터셋이 돼요.
- **개인 위키**: `members/<이름>/wiki/` 아래에 `raw/`(실습 메모, 에러 로그, 참고 링크)와 `pages/`(개념 페이지)를 둬요. LLM이 raw를 개념 페이지로 정리하고, 본인이 읽고 고쳐요.
- **페이지 템플릿**: 한 줄 정의, 왜 필요한가, 최소 예제, 내가 막힌 점, 출처
- **팀 지식 베이스로 올리기**: 개인 페이지를 PR로 `team/wiki/`에 올려요. 조건은 실습으로 직접 확인한 내용, 출처 있음, 리뷰어 1명 승인이에요. 같은 개념을 여러 명이 썼으면 하나로 합쳐요.
- **색인**: `team/wiki/index.md`에 페이지 목록과 한 줄 요약을 유지해요. 정리는 LLM에게 맡겨도 되지만 반영은 PR로 해요.
- **점검**: 단체 세션의 리뷰 시간에 중복, 깨진 링크, 출처 없는 페이지를 LLM으로 찾아 정리해요 (10분 이내).
- **배포**: 2주차에 정적 사이트(MkDocs + GitHub Pages)로 띄우고(선택), 4주차에 RAG `/ask`를 붙이고, 6주차에 k8s로 배포해요.
- **주의**: LLM이 정리한 내용은 틀릴 수 있어요. 실습으로 확인하지 않은 내용은 개인 위키에만 두고 팀 위키에는 올리지 않아요.

## 팀 평가 기준 (3주차에 만들고 7주차까지 사용)

4주차 대회와 7주차 README 표가 같은 잣대로 비교되도록, 3주차에 아래를 팀 공통으로 고정해요.

- **질문셋** `team/eval/questions.jsonl`: 질문, 정답 위키 페이지(또는 청크 ID). 3주차에 20개, 6주차에 k8s 질문 5개를 더해요.
- **평가 스크립트** `team/eval/evaluate.py`: 리트리버를 넣으면 질문셋으로 Recall@k와 MRR@k를 계산하고, 질문당 평균 응답 시간도 함께 출력해요. 3주차에 한 명이 만들고 나머지는 그대로 써요.
  - Recall@k: 정답 문서가 상위 k개 안에 있는 질문의 비율
  - MRR@k: 정답이 처음 나온 순위의 역수 평균 (1위면 1, 2위면 0.5, 못 찾으면 0)
- **청크 ID**: 청킹 직후 각 청크의 `metadata["id"]`에 고유 ID를 붙여요. 질문, 정답, 검색 결과를 잇는 열쇠라 이게 없으면 채점이 틀어져요.
- **기준선(baseline)**: 임베딩 `bge-m3`, `chunk_size=500`, `chunk_overlap=50`, 벡터 검색 `k=5`. 대회에서는 이 기준선 대비 몇 점 올랐는지로 비교해요.
- **채택 규칙**: 새 기법은 기준선보다 점수가 오르고, 늘어난 응답 시간을 감수할 만할 때만 팀 프로젝트에 넣어요.

### 3주차: RAG 기초 (LangChain)

**개인 과제**

- [ ] RAG 파이프라인의 흐름(로드 → 분할 → 임베딩 → 저장 → 검색 → 생성) 정리
- [ ] LangChain으로 팀 위키 로드, `RecursiveCharacterTextSplitter`로 청킹하고 청크마다 `metadata["id"]` 부여
- [ ] `bge-m3` 임베딩으로 Chroma에 저장하고 retriever로 검색
- [ ] LCEL로 검색 + 생성 체인 만들기, 답변과 함께 출처(페이지 이름) 반환
- [ ] `team/eval/evaluate.py`로 내 리트리버의 Recall@5, MRR@5 측정 (스크립트는 이번 주 한 명이 만들어 공유)

**선택 (하나만)**

- [ ] 질문 자동 생성: LLM에게 청크마다 질문 2개를 만들게 하면 그 청크가 정답이 돼요. 사람 라벨링 없이 질문셋을 늘리는 방법이에요. 다만 질문이 청크의 단어를 그대로 따라 쓰기 쉬워 키워드 검색에 유리하게 나올 수 있으니, 공식 질문셋은 사람이 만든 20개로 두고 자동 생성분은 보조로만 써요.

**단체 세션**

- 발표: "임베딩과 벡터 DB는 어떻게 비슷한 문서를 찾는가"
- 팀 평가 기준 확정: 질문셋 20개를 함께 만들고 질문마다 정답 위키 페이지를 적기, 기준선 설정 합의
- 함께 실습: 청크 크기(200/500/1000)를 나눠 맡고, 눈으로 답을 비교하는 대신 `evaluate.py` 점수로 비교

### 4주차: RAG 고도화 + API화

**개인 과제**

- [ ] 아래 둘 중 하나를 적용하고 기준선과 점수 비교
  - 하이브리드 검색: BM25(키워드)와 벡터(의미) 결과를 RRF로 합치기 (LangChain `EnsembleRetriever`). BM25는 고유명사, 숫자, 명령어처럼 정확한 단어에 강하고, 벡터는 표현이 달라도 뜻이 통하는 문서를 찾아요.
  - 리랭커: 벡터로 후보 10~20개를 뽑고 크로스인코더(`BAAI/bge-reranker-v2-m3`, 로컬)로 다시 채점해 상위 5개만 남기기
- [ ] RAG 체인을 FastAPI `/ask` 엔드포인트로 감싸기, 답변과 함께 출처 반환
- [ ] Docker 이미지로 빌드

**선택 (하나만)**

- [ ] 멀티쿼리: 질문 하나를 여러 검색어로 바꿔 검색(`MultiQueryRetriever`)하고 점수 비교
- [ ] 멀티턴: 이전 대화를 보고 후속 질문("그럼 k8s에서는?")을 독립된 검색어로 바꾸는 단계 추가
- [ ] HyDE: 질문으로 가상의 답변 문서를 먼저 만들고 그 문서로 검색. 질문은 짧은데 문서가 길어 검색이 빗나갈 때 효과가 있어요.
- [ ] 위키 색인 방식(LLM이 `index.md`와 링크를 따라 답 찾기) vs 벡터 RAG를 같은 질문셋으로 비교
- [ ] 에이전트 선택 트랙 A단계 (아래 참고)

**단체 세션**

- 검색 품질 비교 대회: 각자 기준선 대비 Recall@5, MRR@5, 질문당 응답 시간을 한 줄씩 표에 적고 발표 (위키 색인 방식도 참가 가능)
- 팀 프로젝트에 쓸 최종 RAG 구성 결정: 채택 규칙에 따라 점수가 오른 기법만
- 팀 역할 분담 (아래 "최종 팀 프로젝트" 참고)

### 5주차: Kubernetes 기초

**개인 과제**

- [ ] Pod, Deployment, Service, Namespace의 관계 정리
- [ ] kind로 로컬 클러스터 만들기

## 에이전트 선택 트랙 (4~6주차, 주당 선택 1개 안에서)

에이전트는 이번 스터디의 4개 핵심 스킬 밖이라 선택이에요. 하고 싶은 사람은 아래 순서대로 한 주에 한 단계씩 해요. 각 단계는 2시간 안에 끝나는 크기이고, 팀 프로젝트에는 넣지 않아요.

| 단계 | 내용 | 확인할 것 |
| --- | --- | --- |
| A. Function Calling | 함수 명세를 JSON 스키마로 쓰고, 모델이 돌려준 `tool_calls`의 함수명과 인자로 실제 함수를 실행한 뒤 `role="tool"` 메시지로 결과를 돌려줘 최종 답 만들기 | 모델이 맞는 함수를 골랐는지, 인자를 맞게 채웠는지 |
| B. ReAct 루프 | 생각 → 행동(도구 호출) → 관찰을 반복하는 루프를 직접 구현하고, `/ask`의 검색기를 도구로 등록 | 최대 반복 횟수와 종료 조건을 꼭 두기 |
| C. Plan-and-Execute 또는 LangGraph | 질문을 먼저 분석해 "어떤 도구로 무엇을 검색할지" 계획을 세우고 실행하기, 또는 LangGraph로 "검색 → 관련성 판단 → 부족하면 재검색" 3노드 그래프 | 단순 RAG 대비 질문셋 점수와 응답 시간 |
| D. 멀티에이전트 | LangGraph로 감독자가 "검색 담당"과 "답변 작성 담당" 중 고르는 작은 예제를 공식 튜토리얼로 실행 | 단일 에이전트 대비 이득이 있는지 |

단계를 할 때마다 위키 페이지 한 장으로 남겨요. 단일 구조보다 몇 % 나아졌는지 수치로 적으면 그대로 포트폴리오 근거가 돼요.

## 최종 팀 프로젝트

목표는 팀 위키(`team/wiki/`)에 질문하면 출처와 함께 답하는 RAG API를 Kubernetes 클러스터에 배포하는 것이에요. 4주차에 역할을 나누고, 5명 기준 예시는 아래와 같아요.

| 모듈 | 담당 | 내용 |
| --- | --- | --- |
| 데이터 파이프라인 |  | 위키 로드, 청킹(ID 부여), 임베딩, 벡터 DB 적재 스크립트와 재적재 Job |
| 검색 (리트리버) |  | 벡터 검색, 하이브리드 또는 리랭커, 4주차 대회에서 채택된 구성 |
| 생성 + 평가 |  | 프롬프트와 생성 체인, 출처 반환, 질문셋과 `evaluate.py` 관리, 개선 전/후 표 |
| API 서버 |  | FastAPI `/ask`, `/health`, 요청 로그(질문, 검색된 문서 ID, 응답 시간) |
| 인프라 |  | Dockerfile, k8s YAML(Deployment, Service, ConfigMap, Secret, PVC, Job) |

**완료 기준**: 클러스터에 배포된 API가 팀 질문셋 25개에 출처와 함께 답하고, Pod를 하나 지워도 서비스가 계속 동작하며, README에 기준선 대비 점수 표가 있으면 통과예요.

### README 골격

1. 한 줄 요약과 문제 정의 (무엇을 풀고, 성공 기준은 무엇인지)
2. 구조도
3. 기술 스택과 선택 근거 (비교한 후보가 있으면 표로)
4. 데이터 (팀 위키 페이지 수, 청킹 설정)
5. 평가표: 기준선 → 적용한 기법별 Recall@5, MRR@5, 응답 시간
6. 실패 분석: 틀린 질문 몇 개를 골라 왜 틀렸는지 (검색 실패인지, 생성 실패인지)
7. 한계와 다음 단계
8. 실행 방법 (`kind`로 띄우는 명령어까지)

**수치 규칙**: 표에는 실제로 돌린 결과만 넣고, 아직 안 잰 칸은 "측정 예정"으로 비워 둬요.

**기여 표**: README 끝에 멤버별로 맡은 모듈과 직접 한 일을 적어요. 나중에 각자 포트폴리오로 쓸 때 본인 몫을 설명할 수 있어요.

## 스터디 이후 심화 (참고)

- **임베딩 파인튜닝**: 팀 위키 청크로 질문을 합성해 `bge-m3`를 대조 학습(MultipleNegativesRankingLoss)으로 다시 학습하고, 같은 `evaluate.py`로 전후를 비교해요. 학습 데이터가 수백 쌍 이상 필요하고 GPU가 있으면 훨씬 수월해서 7주 안에는 넣지 않았어요.
