# 1. 왜 RAG인가

---

## LLM 지식의 한계

사전학습 언어 모델은 지식을 **모델 파라미터 안에** 저장한다. 그래서

- **지식 갱신이 어렵다**: 세상이 바뀌면 다시 학습해야 한다
- **근거를 보여줄 수 없다**: 답이 어디서 나왔는지 모른다
- **환각**: 그럴듯하지만 틀린 사실을 지어낸다

→ 필요한 지식을 **바깥에서 찾아오자**가 RAG의 출발점

---

## RAG 논문 (Lewis et al., NeurIPS 2020)

**두 종류의 기억을 결합**

- **파라메트릭 기억**: 생성 모델 BART-large (언어 능력, 일반 지식)
- **비파라메트릭 기억**: 위키피디아 약 2,100만 문단(100단어 단위)을 벡터로 만든 인덱스
- **검색기 DPR**: BERT 두 개로 질문과 문단을 각각 벡터로 만들고, **내적이 큰 문단**을 고른다

```
질문 → 검색기(DPR) → 상위 k개 문단(5~10개) → 생성기(BART) → 답
```

---

## RAG-Sequence vs RAG-Token

| | RAG-Sequence | RAG-Token |
| --- | --- | --- |
| 문서 사용 | 답 전체를 문서 하나에 기대어 생성 | 토큰마다 다른 문서 참고 가능 |
| 확률 합산 | 문서별로 답을 만든 뒤 합침 | 토큰 단계에서 문서별 확률을 합침 |
| 잘 맞는 경우 | 답이 한 출처에서 나오는 질문 | 여러 출처를 섞어야 하는 생성 |

- 공통: 검색 문서를 **잠재 변수**로 보고 확률을 합산(marginalize) → 근거 문서 라벨이 필요 없다
- 학습: 질문 인코더 + BART만 미세조정, **문서 인코더와 인덱스는 고정** (바꾸면 2,100만 문단 재인코딩)

---

## RAG 논문이 보여준 것

- **오픈 도메인 QA** 4종에서 당시 최고 성능. 문서에 정답 문자열이 그대로 없어도 답을 생성
- 검색 없이 답하는 T5(closed-book), 답 구간을 잘라내는 추출형(REALM 등)보다 우수
- **인덱스 교체 실험**: 2016년 위키 → 2018년 위키로 바꾸기만 해도 바뀐 사실(국가 정상)에 맞게 답이 바뀜 → **재학습 없이 지식 갱신**

**한계**: 검색 붕괴(같은 문서만 가져오고 생성기가 무시), 문서 인코더 고정, **검색이 틀리면 답도 틀린다**

> 💬 지금 실무 RAG는 학습 없이 검색 결과를 LLM 프롬프트에 붙이는 형태. 우리 것도 그렇다. 그래서 "검색이 틀리면 답도 틀린다"가 더 중요해지고, 오늘 검색을 따로 채점하는 이유가 된다.

---

## 논문 RAG vs 우리 RAG

| | 논문 RAG (2020) | 우리 RAG (3주차) |
| --- | --- | --- |
| 문서 | 위키피디아 2,100만 문단 | 팀 위키 15페이지 → 109청크 |
| 검색기 | DPR (질문 인코더 학습) | bge-m3 (학습 안 함) |
| 벡터 저장 | FAISS 인덱스 | Chroma (HNSW) |
| 생성기 | BART (함께 학습) | Gemini API (학습 안 함) |
| 유사도 | 내적 | 코사인 (정규화 벡터) |

```
[미리 한 번]  로드 → 분할 → 임베딩 → 저장
[질문마다]                    질문 임베딩 → 검색 → 생성
```

# 2. 임베딩과 Sentence-BERT

---

## Sentence-BERT가 풀려는 문제 (Reimers & Gurevych, 2019)

BERT로 문장을 비교하면 **너무 느리다**

- BERT에 두 문장을 함께 넣어 1만 문장 중 가장 비슷한 쌍 찾기: 약 5,000만 번 추론, **약 65시간** (V100)
- SBERT로 문장마다 한 번씩 임베딩: **약 5초** (이후 코사인 비교 약 0.01초)

그냥 BERT의 [CLS]나 출력 평균을 뽑아 쓰면? → 문장 유사도가 **평균 GloVe 벡터보다도 낮았다**. 문장 비교용으로 **미세조정**해야 한다.

---

## 구조: 샴(Siamese) 네트워크

```
문장 A → BERT → 풀링 → 벡터 u ┐
                                ├→ 코사인 유사도 cos(u, v)
문장 B → BERT → 풀링 → 벡터 v ┘
   (두 BERT는 가중치를 공유)
```

| 목적함수 | 방식 | 데이터 |
| --- | --- | --- |
| 분류 | (u, v, \|u−v\|) 이어 붙여 softmax | NLI |
| 회귀 | cos(u, v)와 정답 점수의 MSE | STS |
| 삼중항 | 기준이 긍정과는 가깝게, 부정과는 멀게 | 위키 섹션 등 |

- (u, v, |u−v|) 결합이 가장 좋았고 |u−v|가 가장 중요. 분류층은 학습 후 버린다
- 풀링: MEAN, CLS, MAX 비교 → **SBERT 기본값은 평균**

---

## 직접 열어 본 bge-m3

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")
print(model)
```

```
SentenceTransformer(
  (0): Transformer({... 'architecture': 'XLMRobertaModel'})
  (1): Pooling({'embedding_dimension': 1024, 'pooling_mode': 'cls', ...})
  (2): Normalize(...)
)
```

- **Transformer** → 토큰마다 벡터 / **Pooling** → 하나로 / **Normalize** → 길이 1
- SBERT 기본값(평균)과 달리 bge-m3는 **CLS 풀링**

> 💬 질문 던지기: 왜 bge-m3는 평균 대신 CLS를 썼을까?

---

## 토큰 벡터 여러 개 → 문장 벡터 하나

```python
tok = model.encode(sentences[0], output_value="token_embeddings")
print("토큰 벡터:", tuple(tok.shape))
emb = model.encode(sentences, normalize_embeddings=True)
print("문장 벡터:", emb.shape)
```

```
토큰 벡터: (23, 1024)  <- 토큰 수 x 차원
문장 벡터: (5, 1024)   <- 문장 수 x 차원
```

문장 길이와 상관없이 항상 **1024차원 벡터 하나** → 미리 저장해 두고 비교할 수 있다

---

```python

```

# 3. Bi-encoder vs Cross-encoder

---

## 차이는 "두 문장을 언제 만나게 하느냐"

**Bi-encoder**: 따로 인코딩하고 나중에 비교

```
문장 A → 인코더 → u ┐
                    ├→ 코사인 유사도
문장 B → 인코더 → v ┘
```

**Cross-encoder**: 함께 넣어서 바로 판단

```
[CLS] 문장 A [SEP] 문장 B [SEP] → BERT → 점수
```

---

## 비교 요약

| | Bi-encoder | Cross-encoder |
| --- | --- | --- |
| 입력 | 문장을 따로 | 두 문장을 붙여서 한 번에 |
| 상호작용 | 마지막 비교 단계에서만 | 모든 층에서 |
| 미리 계산 | 가능 (벡터 저장) | 불가능 |
| 속도 | 빠름 | 느림 (쌍마다 실행) |
| 정확도 | 조금 낮음 | 높음 (부정어, 어순까지) |
| 주 용도 | 대규모 검색, 후보 추리기 | 소수 후보 정밀 순위 |
| 예 | SBERT, DPR, **bge-m3 (우리)** | 재순위(re-ranker) 모델 |

---

## 실무 파이프라인: 검색 → 재순위 → 생성

```
문서 100만 개
  → ① Bi-encoder로 상위 100개 추림   (빠르게)
  → ② Cross-encoder로 다시 순위 매김 (정확하게)
  → ③ 상위 5개를 LLM에 전달해 답 생성 (RAG)
```

넓게는 빠른 방법으로 거르고, 좁혀진 후보만 정확한 방법으로 판단

> 💬 오늘 만든 파이프라인은 ①과 ③만 있다. ②(크로스인코더 리랭커)를 더하면 순위가 얼마나 좋아질지가 다음 주제.

# 4. 거리 재는 법과 Chroma 함정

---

## 코사인, 내적, L2

- **내적** `a·b = |a||b|cosθ`: 방향 + **길이**에도 영향
- **코사인** `cosθ = a·b / (|a||b|)`: **방향만**. 클수록 가깝다
- **L2** `|a − b|`: 직선 거리. **작을수록** 가깝다

정규화(`|a| = |b| = 1`)하면

- 내적 = 코사인
- L2² = |a|² + |b|² − 2a·b = **2 − 2cosθ**

→ 세 방법의 **순위가 완전히 같아진다**

---

## 직접 확인

```python
a, b = emb[0], emb[1]
cos = a @ b / (np.linalg.norm(a) * np.linalg.norm(b))
dot = a @ b
l2 = np.linalg.norm(a - b)
```

```
cos=0.5621  dot=0.5621  L2=0.9358  2-2cos=0.8758  L2^2=0.8758
```

cos = dot, L2² = 2 − 2cos ✔

---

## Chroma 함정: 기본 거리는 L2

```python
vectorstore = Chroma.from_documents(
    chunks, embeddings,
    ids=[c.metadata["id"] for c in chunks],
    collection_metadata={"hnsw:space": "cosine"},   # 안 쓰면 기본값 L2
)
```

같은 질문 "컨테이너가 꺼진 뒤에도 결과 파일을 남기려면?"

| 순위 | 기본값(L2) | cosine | 청크 |
| --- | --- | --- | --- |
| 1 | 0.7128 | 0.3564 | container-commands-2 |
| 2 | 0.7576 | 0.3788 | 1-docker-concepts-2 |
| 3 | 0.8226 | 0.4113 | 1-docker-concepts-4 |

- 순위는 같고, 점수는 정확히 **2배** (L2² = 2 − 2cos, cosine 거리 = 1 − cos)
- 둘 다 **작을수록 가깝다**

> 💬 그럼 왜 evaluate.py는 cosine으로 고정했을까? 정규화를 깜빡한 모델이라면?

# 5. 벡터 DB와 HNSW

---

## 벡터 DB가 하는 일

- 저장: 청크마다 **id + 벡터 + 원문 + metadata(source, page)**
- 검색: 질문 벡터와 **가장 가까운 벡터 k개** 찾기 (최근접 이웃 탐색, k-NN)

일반 DB는 "값이 같은 행"을 찾고, 벡터 DB는 "**가장 비슷한** 행"을 찾는다

---

## 전부 비교하면 왜 안 되나

**전수 비교(brute force)**: 질문 벡터를 모든 벡터와 하나씩 비교

| 문서 수 | 질문 1개당 곱셈 (1024차원) |
| --- | --- |
| 109 (우리 위키) | 약 11만 번 |
| 100만 | 약 10억 번 |
| 1억 | 약 1,000억 번 |

- 문서 수에 **정비례**해서 느려진다 (O(N))
- 해결: **근사 최근접 탐색(ANN)** — 진짜 1위를 "거의" 맞히는 대신 훨씬 빠르게
- 대표 방법: 클러스터로 나누기(IVF), 벡터 압축(PQ), **그래프 탐색(HNSW)** ← Chroma, FAISS, Qdrant 등이 사용

---

## HNSW의 출발점: 그래프 위에서 걸어가기

각 벡터를 점으로 두고, **가까운 점끼리 선으로 연결**해 둔다 (NSW, Navigable Small World)

```
검색: 아무 점에서 출발
  → 연결된 이웃 중 질문에 더 가까운 점으로 이동
  → 더 가까운 이웃이 없으면 멈춤 (탐욕 탐색)
```

- 모든 점을 보지 않고 **이웃만** 보면서 이동한다
- 문제: 점이 많아지면 한 칸씩 걷는 거리가 길어진다 → 멀리 한 번에 뛰는 길이 필요

---

## H = Hierarchical: 층을 쌓는다

```
층 2:  ●───────────────────●                (점 아주 적음, 먼 연결)
       │                   │
층 1:  ●──────●──────●─────●──────●         (점 조금, 중간 연결)
       │      │      │     │      │
층 0:  ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●       (모든 점, 가까운 연결)
```

- 모든 점은 층 0에 있고, **무작위로 일부만** 위층에도 올라간다 (위로 갈수록 확률이 줄어듦)
- 검색 순서
  1. 맨 위층에서 탐욕 탐색 → 대략 위치를 잡음 (큰 걸음)
  2. 그 점에서 한 층 내려가 다시 탐색 (중간 걸음)
  3. 층 0에서 가까운 이웃을 정밀하게 탐색 → 상위 k개
- 비유: 지도 앱에서 **나라 → 도시 → 동네 → 골목**으로 확대해 가며 찾기 (또는 급행 → 완행 지하철)
- 결과: 문서 수가 늘어도 탐색 단계는 **대략 log N** 수준으로만 늘어난다

---

## HNSW가 얻는 것과 포기하는 것

| | 전수 비교 | HNSW |
| --- | --- | --- |
| 정확도 | 항상 진짜 1위 | 거의 맞음 (가끔 놓침) |
| 검색 속도 | 문서 수에 비례 | 매우 빠름 (대략 log N) |
| 메모리 | 벡터만 | 벡터 + 그래프 연결 정보 |
| 색인 만들기 | 필요 없음 | 그래프를 만드는 시간 필요 |

조절하는 값 (정확도 ↔ 속도)

- **M**: 점 하나가 연결하는 이웃 수. 크면 정확하지만 메모리 증가
- **ef_construction**: 그래프를 만들 때 살펴보는 후보 수. 크면 그래프 품질↑, 색인 시간↑
- **ef_search**: 검색할 때 살펴보는 후보 수. 크면 정확도↑, 검색 시간↑

> 💬 우리 109청크는 전수 비교와 차이가 거의 없는 규모. 그래서 이번 실험의 검색 시간(약 100ms)은 HNSW보다 질문 임베딩 시간이 대부분으로 보인다. HNSW의 효과는 문서가 수십만 개 이상일 때 드러난다

# 6. 실험: 팀 위키 RAG

---

## 로드 → 분할

```python
loader = DirectoryLoader(str(WIKI), glob="*.md", loader_cls=TextLoader,
                         loader_kwargs={"encoding": "utf-8"})
docs = [d for d in loader.load()
        if Path(d.metadata["source"]).name not in ("index.md", "_template.md")]

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
for doc in docs:
    page = Path(doc.metadata["source"]).stem          # 예: docker-compose
    for i, c in enumerate(splitter.split_documents([doc])):
        c.metadata["page"] = page
        c.metadata["id"] = f"{page}-{i}"              # 청크 ID: 채점의 열쇠
```

- 팀 위키 **15페이지 → 109청크**, 평균 348자, 가장 긴 청크 496자

## 평가: 팀 공통 질문셋 25개

```python
from evaluate import evaluate, load_questions
result = evaluate(retriever, load_questions(".../questions.jsonl"), k=5, show_misses=True)
```

- **Recall@5**: 정답 페이지가 상위 5개 안에 있는 질문 비율
- **MRR@5**: 정답이 처음 나온 순위의 역수 평균 (1위 1.0, 2위 0.5, 없으면 0)
- 정답은 **페이지 단위**: 청크 ID는 청크 크기를 바꾸면 달라지니까

| 리트리버 | Recall@5 | MRR@5 | 평균 검색 ms |
| --- | --- | --- | --- |
| bge-m3, 500/50, cosine (기준선) | **1.000** | **0.823** | 108.7 |

- 25개 모두 상위 5개 안에서 찾았지만, **8개는 1위가 아니었다**
- 예: q01 "비밀 키를 코드에 적으면?" → 정답 `api-key-env`가 **4위** (1~3위: docker-concepts, compose, redis)
- 예: q08 "레디스 주소를 localhost로 쓰면?" → 같은 내용을 다룬 다른 페이지가 1위, 정답으로 적은 페이지는 2위

> 💬 1위를 놓친 질문들은 같은 주제를 여러 명이 쓴 페이지가 많다. 질문셋의 정답 목록이 충분한가도 따져 볼 문제.

## 정리

1. **RAG**: 검색으로 찾은 외부 지식을 붙여, 재학습 없이 지식을 갱신하고 근거를 남긴다
2. **Sentence-BERT**: 문장을 한 번씩 벡터로 만들어 두면 대규모 의미 검색이 가능해진다
3. **Bi → Cross → 생성**: 넓게 빠르게 찾고, 좁혀서 정확하게 고른 뒤 생성한다
4. **정규화하면 코사인 = 내적, L2² = 2 − 2cos**. Chroma 기본값(L2)에 주의
