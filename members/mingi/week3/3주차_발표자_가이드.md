## 1. 개념 학습 단계

각 단계는 **읽을 것 → 해 볼 것 → 스스로 답할 질문** 순서예요. 질문의 답이 곧 위키 `## 내 정리`가 되고, 발표 대본의 재료가 돼요. 답을 쓰고 나서 Claude에게 보여 주세요.

### L1. RAG 파이프라인의 흐름 (1일차)

- **읽을 것**: 이미 읽은 RAG 논문(Lewis et al. 2020)의 그림 1, LangChain 공식 문서의 RAG 튜토리얼 개요 부분
- **해 볼 것**: 종이에 `로드 → 분할 → 임베딩 → 저장 → 검색 → 생성` 6칸을 그리고, 각 칸에 "입력이 무엇이고 출력이 무엇인지"를 적어 보기. 색인 단계(미리 한 번)와 질문 단계(매번)를 선으로 나눠 보기
- **스스로 답할 질문**
  - 6단계 중 질문이 들어올 때마다 실행되는 단계는 어디부터 어디까지인가?
  - 논문의 RAG(검색기도 학습)와 우리가 만드는 RAG(검색기 고정, LLM은 API)는 어느 칸이 다른가?
  - 검색이 틀리면 생성은 어떻게 되나? 그래서 이번 주에 검색만 따로 채점하는 이유는?

### L2. 임베딩이란 무엇인가 (1일차)

- **읽을 것**: sbert.net의 첫 페이지와 "Semantic Textual Similarity" 예제
- **해 볼 것**: 아직 코드 없이, 문장 5개를 직접 골라 두기 (2일차 데모에 써요). 비슷한 뜻 2개, 단어는 겹치지만 뜻이 다른 것 1개, 완전히 다른 것 2개. 예상 유사도 순위를 미리 적어 두기
- **스스로 답할 질문**
  - 임베딩이란 무엇인가? "의미가 비슷하다"가 "벡터가 가깝다"로 바뀐다는 건 무슨 뜻인가?
  - 키워드 검색(단어가 겹치는지)과 임베딩 검색은 어떤 질문에서 결과가 갈릴까?
  - bge-m3의 벡터는 몇 차원인가? (2일차에 코드로 확인)

### L3. sentence-transformers (2일차, 발표 핵심)

- **읽을 것**
  - Sentence-BERT 논문 (Reimers & Gurevych 2019, arXiv 1908.10084): 초록, 1장 서론, 그림 1~2, 3장 모델 부분만
  - sbert.net 문서: "Computing Embeddings", "Training Overview"의 손실 함수 소개 부분
  - (선택) BGE M3 논문 (Chen et al. 2024, arXiv 2402.03216) 초록과 그림 1
- **해 볼 것** (`rag.ipynb`의 "임베딩" 섹션 앞에 데모 셀로)

  ```python
  from sentence_transformers import SentenceTransformer
  model = SentenceTransformer("BAAI/bge-m3")
  print(model)                       # 모듈이 몇 단계로 이어져 있는지, 각 단계 이름 확인

  sentences = [...]                  # L2에서 고른 문장 5개
  emb = model.encode(sentences, normalize_embeddings=True)
  print(emb.shape)                   # (문장 수, 차원)

  tok = model.encode(sentences[0], output_value="token_embeddings")
  print(tok.shape)                   # 토큰 수 x 차원: 문장 하나가 원래는 벡터 여러 개

  print(model.similarity(emb, emb))  # 5x5 유사도 표: L2에서 적은 예상과 비교
  ```

- **스스로 답할 질문**
  - sentence-transformers는 무엇인가? 일반 BERT(혹은 Transformer)와 무엇이 다른가?
  - `print(model)`에 나온 단계들은 각각 무슨 일을 하나? 특히 Pooling은 토큰 벡터 여러 개를 어떻게 하나로 만드나? bge-m3는 어떤 pooling 방식을 쓰나?
  - BERT에 두 문장을 같이 넣는 방식(cross-encoder) 대신 따로 임베딩하는 방식(bi-encoder)을 쓰는 이유는? 문서가 1만 개일 때 두 방식의 계산량을 비교하면? (논문 서론에 숫자가 있어요)
  - 이런 모델은 "비슷한 문장은 가깝게"를 어떻게 배우나? (양성 쌍, 음성 쌍, 배치 안의 다른 문장을 음성으로 쓰는 방식)
  - 유사도 표에서 예상과 다르게 나온 쌍이 있었나? 왜 그랬을까?

### L4. 유사도와 거리 (2일차)

- **읽을 것**: Chroma 문서의 컬렉션 설정(distance / `hnsw:space`) 부분
- **해 볼 것**
  - 정규화한 벡터 두 개로 코사인 유사도, 내적, L2 거리를 직접 계산해서 셋의 관계 확인 (numpy 3줄)
  - Chroma에 `collection_metadata` 없이 만든 경우와 `{"hnsw:space": "cosine"}`으로 만든 경우, `similarity_search_with_score`의 점수가 어떻게 다른지 출력
- **스스로 답할 질문**
  - 코사인, 내적, L2는 각각 무엇을 재나? 벡터를 정규화하면 셋의 순위가 왜 같아지나?
  - Chroma의 기본 거리는 무엇인가? 점수가 클수록 가까운가, 작을수록 가까운가?
  - `evaluate.py`가 cosine으로 고정한 이유를 내 말로 설명하면?

### L5. 벡터 DB와 근사 검색(HNSW) (3일차)

- **읽을 것**: HNSW 논문 (Malkov & Yashunin 2016, arXiv 1603.09320)의 그림 1만, 또는 Pinecone 블로그의 HNSW 설명 글
- **해 볼 것**: 청크 수를 세고, 질문 하나당 검색 시간(`evaluate.py`의 평균 검색 시간)을 기록해 두기
- **스스로 답할 질문**
  - 벡터 DB는 일반 DB와 무엇이 다른가? Chroma는 우리 파이프라인에서 무엇을 저장하나? (벡터, 원문, metadata)
  - 문서가 100만 개면 질문 벡터와 전부 비교할 수 있나? 근사 검색(ANN)은 무엇을 포기하고 무엇을 얻나?
  - HNSW 그림에서 위층과 아래층은 각각 무슨 역할인가? (지하철 급행/완행 같은 비유를 직접 만들어 보기)

### L6. 청킹과 임베딩 (3일차, 함께 실습으로 연결)

- **해 볼 것**: `evaluate.py`로 청크 200/500/1000을 돌려 표 채우기 (2절 3일차)
- **스스로 답할 질문**
  - 청크가 너무 작으면/크면 검색과 생성에 각각 무슨 일이 생기나? overlap은 왜 필요한가?
  - 긴 청크는 왜 임베딩의 의미가 흐려질까? (L3의 pooling과 연결)
  - 우리 위키 페이지는 1~3KB로 짧아요. 1000자 청크면 사실상 페이지 하나가 청크 하나인데, 이 결과를 큰 문서에도 그대로 적용해도 될까?
  - 내 위키는 `### Q.` 제목으로 나뉘어 있어요. 글자 수로 자르는 것과 제목 단위로 자르는 것 중 무엇이 나을까?

## 2. 실습 단계

### 1일차: 환경, 로드, 청킹 (스레드에 보낸 1~5단계)

1. `git checkout main` → `git pull` → `git checkout -b mingi/week3`
2. `members/mingi/week3/`에 가상환경, 패키지 설치, `.env`(Gemini 키)와 `.env.example`
3. 저장소 루트에서 `python scripts/merge_wiki.py`로 팀원 위키를 `team/wiki/`에 모은 뒤, `rag.ipynb` 섹션 1 "로드": `DirectoryLoader("../../../team/wiki", glob="*.md", ...)`로 불러오고 `index.md`, `_template.md`는 빼요
   - 확인: `len(docs)`, `docs[0].metadata["source"]`
4. 섹션 2 "분할": `RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)`, 청크 ID `페이지이름-번호` (예: `docker-compose_mingi-0`)
   - 확인: 청크 수, 가장 짧은/긴 청크 길이, 청크 하나의 metadata
   - ID 형식은 `team/eval/evaluate.py`의 `build_retriever`와 같게 맞춰요
5. bge-m3 미리 받기 (약 2GB)

### 2일차: 임베딩 데모, 저장, 검색, 생성

1. 섹션 3 "임베딩": L3의 데모 셀 (모델 구조, shape, 유사도 표). 발표 화면으로 그대로 써요
2. 섹션 4 "저장": `HuggingFaceEmbeddings("BAAI/bge-m3", encode_kwargs={"normalize_embeddings": True})` + `Chroma.from_documents(..., collection_metadata={"hnsw:space": "cosine"})`
   - 확인: L4 실험 (기본 거리 vs cosine 점수 비교)
3. 섹션 5 "검색": `vectorstore.as_retriever(search_kwargs={"k": 5})`
   - 확인: 질문 2~3개로 top-5 청크 ID와 점수 출력 (`similarity_search_with_score`)
4. 섹션 6 "생성": LCEL 체인 `{"context": retriever | 포맷함수, "question": RunnablePassthrough()} | prompt | llm | StrOutputParser()`
   - LLM: `langchain-google-genai`의 `ChatGoogleGenerativeAI(model="gemini-3.8-flash")` (2주차와 같은 모델, 키는 `.env`)
   - 프롬프트에 "문서에 없으면 모른다고 답해" 넣기
   - **출처 반환**: 답과 함께 검색된 청크의 페이지 이름(중복 제거)을 돌려주기. 힌트: `RunnableParallel`로 `context`와 `answer`를 같이 내보내거나, 검색을 먼저 하고 결과를 체인에 넘기기
   - 확인: 위키에 있는 질문 1개, 없는 질문 1개 (모른다고 답하는지)

### 3일차: 채점, 청크 비교, 발표 준비

1. 내 노트북 리트리버 채점
   ```python
   import sys; sys.path.append("../../../team/eval")
   from evaluate import evaluate, load_questions
   evaluate(retriever, load_questions("../../../team/eval/questions.jsonl"), k=5, show_misses=True)
   ```
2. 저장소 루트에서 청크 비교 3번 (함께 실습 리허설, `team/wiki`가 최신인지 먼저 `python scripts/merge_wiki.py`)
   ```
   python team/eval/evaluate.py --chunk-size 200 --overlap 20
   python team/eval/evaluate.py --chunk-size 500 --overlap 50
   python team/eval/evaluate.py --chunk-size 1000 --overlap 100
   ```
   | chunk_size | overlap | 청크 수 | Recall@5 | MRR@5 | 평균 검색 ms |
   | --- | --- | --- | --- | --- | --- |
   | 200 | 20 | | | | |
   | 500 | 50 | | | | |
   | 1000 | 100 | | | | |
3. `--show-misses`로 틀린 질문 2~3개를 골라 "왜 틀렸을까" 메모 (발표 마지막에 쓰기 좋아요)
4. 발표 흐름 정리 (3절), PR 올리기

## 3. 발표 15분 뼈대

내용은 민기 님이 1절 질문에 쓴 답으로 채워요. 화면은 슬라이드 대신 `rag.ipynb`를 그대로 보여 줘도 돼요.

| 시간 | 주제 | 보여 줄 것 | 재료 |
| --- | --- | --- | --- |
| 2분 | RAG가 왜 필요한가, 6단계 흐름 | 파이프라인 그림 | L1 |
| 4분 | 임베딩과 sentence-transformers | `print(model)`, 토큰 벡터 → 문장 벡터, 유사도 표 | L2, L3 |
| 2분 | bi-encoder를 쓰는 이유 | 계산량 비교 숫자 | L3 |
| 2분 | 거리 재는 법과 Chroma 함정 | 기본 거리 vs cosine 점수 | L4 |
| 2분 | 벡터 DB와 HNSW | 그림 1장 | L5 |
| 3분 | 우리 파이프라인 + 채점 방식, 함께 실습 안내 | 답 + 출처 출력, `evaluate.py` 결과 한 줄 | 2절, L6 |

준비 팁

- 발표 끝에 "팀원에게 던질 질문" 1개를 넣으면 함께 실습으로 자연스럽게 넘어가요. (예: 청크가 클수록 점수가 오를까, 내릴까?)
- 대본을 다 쓰지 말고, 시간 칸마다 "꼭 말할 문장 한 줄"만 적어 두는 걸 추천해요.
