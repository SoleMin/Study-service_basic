## 내 정리

### Q. Redis란 무엇인가?

서버에서 캐쉬를 저장해서 사용할 수 있는 DB개념의 시스템

여기서는 LLM모델의 질문을 캐쉬로 저장해서 이미 저장된 질문이면 캐시에서 답안을 불러내서 사용했음

### Q. 캐시란 무엇이고 왜 쓰나? 캐시 히트와 미스는 각각 어떻게 동작하나?

```json
{
  "answer": "안녕하세요! 반갑습니다. 오늘 어떤 도움이 필요하신가요?",
  "cached": false,
  "elapsed_ms": 184095.4982000003
}
```

```json
{
  "answer": "안녕하세요! 반갑습니다. 오늘 어떤 도움이 필요하신가요?",
  "cached": true,
  "elapsed_ms": 0.9623000005376525
}
```

이미 저장된 질문들을 저장하기 위한 시스템,캐시 히트일경우 캐시에서 답안을 불러내 사용했고 미스일 경우 새로 답변을 생성하기 위해 api를 호출했음

위의 예시가 캐시저장전/후의 시간을 비교한것

### Q. TTL이란 무엇인가? 몇 초로 정했고 왜?

redis에 저장한 값의 유효기간, 지금은 `3600`(1시간)으로 설정했고 1시간이 지나면 값이 삭제됨, 너무 짧으면 캐시를 하는 효과가 줄어들고 너무 크게되면 값이 변경되지 않고 너무 오래동안 가지고 있게됨

### Q. 질문을 그대로 키로 쓰지 않고 sha256으로 바꾼 이유는?

질문을 항상 64자의 키로 매핑하기 위해, 보안을 위해.

## Claude 피드백

- **Q1 (Redis)**: 보태면 Redis는 데이터를 **메모리**(RAM)에 `키 → 값`으로 저장하는 저장소라 매우 빨라요. 캐시 말고도 세션, 대기열 등에 쓰여요. 기본 설정에선 재시작하면 데이터가 사라질 수 있어서 "원본"보다는 "빠른 사본" 보관용이에요.
- **Q2 (캐시, 수정)**: "질문을 저장하기 위한 시스템"보다는 "**비싼 작업의 결과를 저장해 두고 다시 쓰는 것**"이 캐시예요. 히트는 키가 있으면 바로 반환, 미스는 API를 호출한 뒤 결과를 TTL과 함께 저장해요. 측정으로 히트/미스 차이를 보여 준 건 아주 좋아요.
- **측정 값 확인**: 1번째 호출이 184,095ms(약 3분)인데, Gemini 호출은 보통 수 초 안에 끝나요. 첫 연결 지연이나 재시도가 섞였을 수 있으니 한 번 더 재 보면 좋아요. 히트가 1ms 아래로 나온 결과는 정상이에요.
- **주의할 점**: 키가 질문 문자열과 **정확히 같을 때만** 히트예요. "안녕"과 "안녕하세요"는 서로 미스예요. 의미가 비슷한 질문까지 묶는 건 RAG 주차의 임베딩과 연결돼요.
- **Q3 (TTL)**: 정확해요. TTL은 메모리가 무한히 차는 것도 막아 줘요. `docker compose exec redis redis-cli TTL <키>`로 남은 시간을 직접 볼 수 있어요.
- **Q4 (sha256, 보완)**: 64자 고정은 맞아요. "보안"은 절반만 맞아요. 키 목록에서 질문 원문이 안 보이는 효과는 있지만, 답변(값)은 그대로 저장되니 암호화는 아니에요. 핵심 이유는 질문이 아무리 길거나 줄바꿈, 한글이 섞여도 **항상 같은 길이의 안전한 키**가 된다는 점이에요. 나중에 모델 이름을 함께 해시에 넣으면 모델을 바꿨을 때 옛 답변이 섞이지 않아요.
