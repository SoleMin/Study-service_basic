# RAG 파이프라인의 흐름 (3주차)

## 내 정리

### Q. RAG란 무엇인가? 왜 LLM에 바로 묻지 않고 검색을 붙이나?

모든 정보를 LLM에 넣을 수 없고 만약 정보가 최신화라도 되면 학습을 다시 시켜야 하는 비용같은 문제가발생할 수 있ㅇ므

RAG는 이를 반영해 외부에서 검색을 해 LLM의 데이터 생성에 사용한다는 컨셉

### Q. 로드 → 분할 → 임베딩 → 저장 → 검색 → 생성, 각 단계의 입력과 출력은 무엇인가?

- **로드**: 데이터 파일
- **분할**: 읽어온 데이터 문서를 작은 문서들로 분리(청킹)
- **임베딩**: BERT와 같은 임베딩 모델을 사용해 자연어 문서를 벡터로 변환
- **저장**: 변환된 벡터들을 DB를 사용해 저장
- **검색**: 들어온 자연어의 입력과 DB에 있는 벡터들의 코사인 유사도를 이용해 답변에 참고할 수 있는 문서 검색
- **생성**: 검색단계에서 찾은 문서와 자연어를 이용해 LLM모델의 입력으로 사용해 답변 생성

### Q. 이 중 미리 한 번만 하는 단계(색인)와 질문이 올 때마다 하는 단계는 어디서 나뉘나?

로드,분할,임베딩은 한번 미리 하게 되고 검색은 매 질문에 따라 문서가 달라지기 때문에 매번 하게 된다.

### Q. 논문의 RAG(Lewis et al. 2020)와 내가 만든 RAG는 어디가 같고 어디가 다른가?

논문의 RAG는 찾아온 데이터로 실제 학습까지 진행하는 튜닝 방법을 제시했지만

이 페이지에서는 실제로 학습은 진행하지 않고 학습된 모델을 불러와 사용하기만 했다.

## Claude 피드백 (2026-11-10)

- **Q1 (RAG란)**: 맞아요. "다시 학습시키는 비용"이 핵심이고, 정리하신 `rag_summary.md`의 나머지 두 한계도 같이 쓰면 완성돼요. **근거를 보여 줄 수 없다**(출처 반환으로 해결)와 **환각**(문서에 있는 내용만 쓰게 해서 줄임)이에요.
- **Q2 (단계별 입출력)**: 각 단계가 **하는 일**은 정확해요. 질문이 "입력과 출력"이라 한 단계 더 나가면 좋아요.
  - 로드: 파일 → Document(본문 + metadata), 15개
  - 분할: Document → 청크 + 청크 ID, 109개
  - 임베딩: 청크 텍스트 → 1024차원 벡터. 우리가 쓴 건 BERT 계열인 bge-m3(XLM-RoBERTa 기반)예요
  - 저장: 벡터 + 원문 + metadata → Chroma 컬렉션
  - 검색: 질문을 **같은 모델로 임베딩한 벡터** → 가까운 청크 5개
  - 생성: 질문 + 청크 5개(프롬프트) → 답 + 출처
- **Q3 (색인 vs 질문마다)**: 한 군데만 고치면 돼요. 미리 하는 단계에 **저장**까지 들어가요(로드, 분할, 임베딩, 저장). 그리고 매번 바뀌는 건 문서가 아니라 **질문**이에요. 질문이 올 때마다 질문 임베딩 → 검색 → 생성을 하고, 문서는 위키가 바뀔 때만 다시 색인해요.
- **Q4 (논문 vs 우리)**: 핵심(우리는 학습 없이 불러와서만 씀)은 정확해요. 다만 논문은 "찾아온 데이터로 학습"한 게 아니라, **정답 답변**으로 질문 인코더와 생성기(BART)를 함께 학습했고 문서 쪽(문서 인코더, 인덱스)은 고정했어요. 학습을 안 하면 간단하고 모델을 바꾸기 쉬운 대신, 검색이 틀려도 그걸 고쳐 줄 학습 신호가 없다는 차이도 덧붙이면 좋아요.
